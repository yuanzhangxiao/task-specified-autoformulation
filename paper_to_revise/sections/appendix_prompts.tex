\section{Prompts and model-facing context}
\label{app:prompts}

We separate the public scientific task from the instructions for each modeling
stage. The task specifies what the model must explain and which quantities are
available; stage instructions specify the decision the proposer or critic must
return. Below, gray boxes reproduce fixed prompt text or explicitly labeled
excerpts. Line wrapping is adjusted for readability. Angle-bracketed fields in
the context template denote values inserted at runtime. That template is a
schematic description, not a recorded model response. Per-call JSON schemas,
model-specific equations, and numerical evidence are omitted from the fixed-text
listings.

These prompts describe the shared-process, multiple-target pipeline used in the
final component campaign. Earlier pilot runs used versioned predecessors. The
public benchmark brief and its channel declarations accompany construction and
revision. Training observations can inform the proposer, and parameters are
fitted on training trajectories. Validation selects among admissible fitted
candidates; test results are not proposal or selection inputs. The scientific
critic receives symbolic models and public context, without fitted parameter
values, fit scores, or trajectories. Its findings are advisory.

\subsection{Public task specification}
\label{app:prompt-task}

Each public brief has six sections: task specification, available data, modeling
requirements, plausibility constraints, intended use, and required response.
The following are the task-specific mechanism clauses for the evaluated cases.
Changing from easy to hard changes the available channels, not the T1 or T2
mechanism clause. Canonical and perturbed dynamics use the same task wording;
the altered reference equation is not disclosed to the proposer. Obfuscation
replaces physiological names with public functional descriptions.

% Source: benchmarks/phase_b_public.py:phase_b_task_mechanism_lines
% Whitespace-normalized SHA256: d2cad5a92e5929ddda6ceed841b7b7e6f5dd6314581a3a3182601ce693429236
\begin{afpromptbox}{Public mechanism clauses (verbatim; case headings added)}
Dalla Man T1 (named; easy or hard)
- a causal mechanism through which meal timing and meal amount contribute to
the observed plasma-glucose mass.

Dalla Man T1 (obfuscated; easy)
- a causal mechanism through which input timing and magnitude contribute to
the observed target.

Dalla Man T2 (named; easy or hard)
- a causal pathway through which meal timing and meal amount contribute to
the observed plasma-glucose mass.
- a delayed insulin-action pathway through which plasma insulin regulates
the insulin-dependent contribution to total glucose disposal U(t).

CSTR (named; easy)
- a reactor-temperature balance that distinguishes feed transport, reaction
heat generation, and heat exchange with the jacket.

Alien device (functional; easy)
- input-driven memory and its causal contribution to the observed output.
\end{afpromptbox}

The T1 clause does not prescribe a particular latent compartment or an insulin
delay. T2 explicitly requests a delayed insulin-action pathway. Channel availability
is equally important: a measured target must be generated during rollout, whereas
a supplied auxiliary may be used as a prescribed trajectory. For example, the
named T1-easy brief contains the following data contract. The benchmark appendix
lists the corresponding channels for the other cases.

The common modeling and plausibility instructions are reproduced below. These
are scientific expectations; their presence in the prompt is not a claim that
every property, such as global well-posedness, is proved by the runtime.

% Source: benchmarks/phase_b_public.py:render_phase_b_prompts
% Whitespace-normalized SHA256: 90475d025bfaa5a562a28959bfb462d0468e2159e9579ec63d1c87e392ac7ae7
\begin{afpromptbox}{Common public instructions (verbatim sections C--E)}
C. Modeling requirements

1. Propose an explicit continuous-time model that generates every target
channel.
2. Include a finite-dimensional causal representation of every task-required
mechanism.
3. Use globally shared equations and parameters across trajectories.
4. Latent states may be introduced when scientifically useful, but every
modeled state must have an explicit governing equation and a causal
initialization from available information.
5. Required mechanisms may not be represented as free time series, per-time
fitted values, unconstrained residuals, lookup tables, or functions of
future observations.
6. Every right-hand side and generated process must have an explicit
analytic form. Arbitrary neural-network vector fields are not allowed.
7. Explain how selected inputs, auxiliaries, states, and generated processes
contribute to each target equation.
8. Keep the model parsimonious and task-sufficient rather than
reconstructing mechanisms unrelated to the stated objective.

D. Constraints and plausibility requirements

Causality: every generated mechanism must depend only on present and past
inputs, available channels, and modeled states. Intervention consistency:
the same mechanism and parameters should apply across input timings,
magnitudes, and trajectories. Dynamic plausibility: delayed or persistent
mechanisms should have explicit initialization and timescales, and transient
contributions should return toward baseline when appropriate. State
constraints: quantities declared as nonnegative should remain nonnegative;
signed deviations and net rates must be identified. Balance consistency:
source, sink, and exchange terms must have coherent signs, scaling, and
interpretations. Well-posedness: the equations should generate unique,
finite trajectories under the supplied and unseen admissible conditions.

E. Intended use

The model will be used to explain the stated mechanisms and to predict
complete responses under new input schedules and initial conditions. Favor a
model whose states and terms retain a stable scientific interpretation
across these conditions, not merely a local curve fit.
\end{afpromptbox}

Section F asks for the state/process list, equations, target mappings, mechanism
explanations, input encoding, initial conditions, parameter restrictions, and
plausibility checks. In Autoformalism, stage-specific JSON schemas collect these
objects through separate calls. The proposer does not return one unrestricted
program or a free-form reconstruction of the reference model.

\subsection{Variables, shared processes, and topology}

Variable identification assigns each quantity a scientific role and a supplied,
differential, algebraic, or unused definition. The runtime provides the current
inventory and a mechanism/target agenda item. Below is the fixed instruction with
the shared-process guidance enabled. A target must be generated even though its
training trajectory is observed.

% Source: search/staged_topology_prompts.py + search/shared_process_guidance.py
% Whitespace-normalized SHA256: 020899b4159884c9c8e3abf9512da66f4843f5eae4ec3518b58f520200c66bd3
\begin{afpromptbox}{Variable identification (verbatim system prompt; sharing enabled)}
You perform only variable identification for a continuous-time scientific
model. The runtime supplies an authoritative public task brief, one
mechanism/target agenda item, and the complete current variable inventory.
Return only the structured response required by the response schema.

For each variable relevant to the agenda item, choose exactly one candidate
definition: supplied, differential, algebraic, or unused, and give one
concise scientific role. Public-data roles, units, availability, target
status, and mechanism requirements are runtime-owned context; do not repeat
or revise them. Data availability is distinct from candidate generation.
Every public target must be generated by the candidate, so define each
target as differential or algebraic, never supplied or unused. Supplied
auxiliaries and inputs may remain supplied even when they appear on later
right-hand sides. You may address multiple displayed mechanisms together and
may reuse existing variables. A public variable currently marked unused may
be activated by returning the same public name with its intended supplied,
differential, or algebraic definition. This is the only definition update
allowed within variable identification. Every active public variable and
every internal variable must preserve its accepted name and definition; any
other change requires an explicit later inventory revision. The runtime
retains its first accepted scientific role if later wording differs. Use
scientifically meaningful states and algebraic processes.

Do not propose equations, right-hand-side dependencies, interaction terms,
functions, parameter names or values, initial values, ranges, scopes,
observation mappings, candidate or term identifiers, hashes, validation
claims, or summaries. Do not emit prose outside the concise scientific_role
fields. A valid empty variable list is allowed when the displayed inventory
already serves the agenda item.

Shared-process modeling guidance (optional, not an extra task requirement):
Distinguish a state that stores memory from an algebraic process evaluated
from current states and supplied channels. An algebraic process has no
independent initial condition. Use one when the same scientifically
meaningful law is needed in several equations; do not add states or
processes just to increase reuse. Keep the model task-sufficient. Supplied
auxiliaries need not be modeled merely to create a second consumer. A
reduced model may need no shared process. A common source does not imply a
common contribution or equal coefficients. A transfer, a converted
contribution and a shared response are different claims. For a same-unit
transfer, one law may enter one balance negatively and another positively.
Different units/volumes may require explicit conversion factors. For a
shared response, independent consumer gains can be scientifically necessary.
Do not infer conservation, positivity, or parameter equality from similar
syntax or opposite signs. A signed process and internal differences remain
permitted.

During variable identification, a new algebraic variable may organize a
reusable scientific law even if the same law could be written inline. Use
the existing algebraic definition and scientific_role fields. Describe its
meaning and intended reuse concisely. Do not emit its equation or parameters
at this stage. Distinct memory states still need distinct scientific roles;
avoid redundant copies.
\end{afpromptbox}

An optional subsequent call proposes named instantaneous processes. Their uses
refer to the same defining law and parameters. The proposer may return no such
processes; shared notation alone does not certify conservation. A second call
jointly assigns the signs and conversion dependencies of each process's uses.

\begin{afpromptbox}{Optional process proposal (verbatim system prompt)}
Propose scientifically meaningful instantaneous processes after variable
selection. Return the requested JSON. Each process has one function, defined
later, and may be used by one or several equations. It has no independent
memory or initial condition. A shared process reuses that SAME law and its
parameters in every use.

Give its name, depends_on, used_in_equations_for, and scientific_meaning.
Use only the displayed eligible names. depends_on lists variables
determining the law; used_in_equations_for lists variables whose modeled
equations contain it. Supplied inflows, geometry, thresholds and initial
readings have no modeled equations and cannot appear in
used_in_equations_for. A measured target CAN have a modeled equation. A

No functions, parameters, initial conditions or numeric values at this

\begin{afpromptbox}{Joint topology of process uses (verbatim system prompt)}
Complete the topology of the displayed process uses together. The process
will have ONE defining function of its declared depends_on variables. For
each declared equation target, give its outer_weight_sign,

Do not repeat the process in conversion_sources. Those are only additional
variables needed to convert or scale the process contribution, not a

opposite signs or equal gains from the name alone. For a transfer, preserve

For ordinary terms, the topology stage chooses grouped dependencies and an outer
weight sign. The excerpt below explains this division of responsibility. A sign
constrains the outer scalar weight, not the global monotonicity of an arbitrary
nonlinear expression. When process contributions have already been supplied,
the topology request asks only for additional terms.

\begin{afpromptbox}{Ordinary equation topology (verbatim opening and sign-policy excerpt)}
You perform only equation-topology construction for one selected generated
variable. The selected left-hand side, its differential or algebraic
definition, the frozen variable inventory, and the allowed source names are
authoritative. Return only the structured response required by the response
schema.

For a normal equation-topology response, return one or more interaction
terms and set inventory_revision to null. Partition the right-hand side into
scientifically meaningful terms. Each term gives its complete joint source
set, outer_weight_sign, and one concise scientific role. Keep variables
together in one source set when their joint interaction matters; do not
flatten a multivariate interaction into unrelated edges. An empty source set
is permitted only for a scientifically justified constant or baseline
contribution. The required outer_weight_sign is positive, negative, or
unrestricted; it has no default. Positive and negative fix the sign of an
identifiable scalar weight multiplying the complete contribution, and the
runtime applies the corresponding outer assembly operator exactly once.
Unrestricted lets the later function own a signed coefficient, including a
signed baseline or offset. The sign decision does not claim that the
complete later interaction function is globally nonnegative, sign-definite,
or monotone over every possible source value.

The runtime may display an interaction_polarity_policy for the selected
equation. When it is present, an exact source set listed under
fixed_exact_source_sets must use that displayed fixed sign. Every other
source set follows unfixed_source_ownership. If it is
runtime_requires_unrestricted, use default_outer_weight_sign, which is
unrestricted. If it is proposer, choose positive, negative, or unrestricted
using the public scientific context and the term's intended role. Do not
infer scientific facts from hidden equations. An explicit public fixed sign
is authoritative; otherwise the proposer owns the scientific decision and
the runtime preserves it.
\end{afpromptbox}

\subsection{Functional forms and causal initialization}

Once a topology is available, the proposer fills identified function slots.
A slot is one contribution to one selected equation, with its declared source
set, scientific role, and assembly sign. The current delivery format uses
\texttt{interaction\_id} to identify slots; array order is immaterial. A function
contains only its RHS and parameter declarations. The runtime retains valid
slots and can repair failed slots without regenerating unrelated equations.

% Source: search/function_delivery.py:system_prompt
% Whitespace-normalized SHA256: 3694f90f2658987daa84cc7ea71857fd8a64b31a18bcd2383759b221869482f3
\begin{afpromptbox}{Function construction (verbatim effective system prompt)}
You assign scalar functional forms for every runtime-selected interaction
term on one left-hand side of a continuous-time scientific model. The frozen
variable inventory, equation topology, selected left-hand side, differential
or algebraic definition, ordered term slots, complete grouped source sets,
outer weight signs, and scientific roles are authoritative. Return only the
structured response required by the response schema: a functions array. Each
entry adds interaction_id from requested_slots. Return one entry per
requested slot; order is immaterial.

Each returned expression fills only the corresponding inner FUNCTION slot.
It is one scalar right-hand-side contribution, not a complete equation.
Within each slot use every displayed source at least once and no other
state, process, public channel, or time symbol. After parameter names are
removed, its symbol set must equal that slot's grouped source set exactly.
An empty source set permits a scientifically justified constant or
parameter-only contribution. Each slot contains a runtime-owned
functional_obligation. When requires_nonlinear_source_dependence is true, a
linear gain or identity is invalid: that slot must contain explicit
nonlinear dependence on at least one displayed source through the admitted
restricted grammar. For positive and negative slots the runtime applies
every frozen outer assembly sign exactly once. For a slot shown as ``d(x)/dt
= ... - (FUNCTION)``, return ``x / tau`` rather than ``-x / tau``. An
unrestricted slot is displayed as ``+ (SIGNED_FUNCTION)``; there the
expression owns its direction and may be signed or sign-changing.

Construct the terms as one scientifically coherent equation. Preserve
required nonlinear behavior. Introduce fitted gains, rates, scales, time
constants, or shape parameters when unknown strength, conversion,
relaxation, saturation, or curvature requires them. When
parameter_identity_policy is interaction_local, parameter names are local
mnemonics and the runtime deterministically namespaces them by interaction;
repeated spelling cannot create sharing. Under a preserve policy, reuse a
name only when the same physical quantity and qualitative role genuinely
apply to both slots. Identity source expressions are valid only for known,
unit-compatible balance contributions.

The restricted grammar permits binary +, -, *, /, and Python **; unary + and
-; finite integer or floating-point literals with magnitude at most 1e12;
one- argument abs, exp, log, sigmoid, softplus, sqrt, and tanh; and min or
max with 2--64 positional arguments. An exponent after ** must be an integer
literal with absolute value at most 16. Conventional symbol(t) is normalized
only to that same scalar symbol. Comparisons, conditionals, Boolean
operators, indexing, attributes, keywords, strings, arrays, arbitrary calls,
and ^ are unsupported. Each expression is limited to 4096 characters, 512
AST nodes, and depth 64.

For each function declare every parameter used in that expression exactly
once, including a shared parameter declared in another slot. Declare no
unused parameter. Each declaration contains only name and role. Reused names
must keep one role across the batch and the accepted runtime registry.
Supported roles are coefficient, nonnegative_coefficient, rate,
time_constant, scale, positive_shape, offset, shape. Under a runtime policy
explicitly identified as certified_outer_gain, runtime may correct
coefficient to nonnegative_coefficient only for one AST-certified direct
outer scalar multiplier of a fixed positive or negative slot. Nested
coefficients and every coefficient in an unrestricted slot remain signed;
all ambiguous cases remain errors.

Do not emit assignments, derivatives or left-hand sides, repeated outer
signs, source lists, topology edits, mechanism IDs, parameter values,
ranges, scopes, units, descriptions, fitted results, initial values, hashes,
validation claims, revision requests, summaries, or prose. Do not repair or
route to another equation. The runtime audits every slot independently. The
frozen calling policy either treats the batch as one transaction or retains
valid slots and sends only failed slots to a later focused atomic repair;
one slot can never silently alter another. The requested_slots map is the
authoritative list of blanks to fill. The whole model is context only.
runtime_supplied_slots are already filled and must NOT be returned. Do not
split one grouped-source function into multiple returned terms. A shared
process law is defined once; its consumer uses are runtime supplied. Return
only its intrinsic scalar RHS, without a name or equals sign. Signs and
consumer conversions shown in assembly_contract are applied by the runtime.
Conversion-owned supplied fixed covariates may be absent from the intrinsic
law. Other dependency changes and conversion decisions use a subsequent
focused repair.
\end{afpromptbox}

A failed construction slot can receive the following focused repair instruction,
together with the failed check and the current assembled contributions. Explicit
dependency revisions are therefore distinct from silently introducing an extra
variable into an accepted source set. Broader public-pathway failures may expose
the displayed companion slots for a coordinated repair. Restricted-grammar
delivery instructions are appended by the calling adapter.

Return only the requested JSON. Define one intrinsic law, before its

Runtime derives names from your expression. Signs, shared identities and

map are both fitted on training data and then held fixed as policies. A causal
map may produce different initial values for different trajectories, using only
the permitted initial observations and inputs. It cannot use the rest of a
validation or test target trajectory.

\subsection{Fitted-model revision and numerical feedback}

Revision receives the complete current equations and a compact comparison of
observed and predicted training responses. It may alter coupled equations,
initialization, or mappings for multiple targets. New parameters are declared
once; references to existing parameters retain their declarations. Numerical
parameter tuning remains the fitter's responsibility. The final component
campaign uses the whole-model form below, which removes the earlier small
patch-count quotas while retaining expression and serialization limits.

% Source: search/response_revision.py:WHOLE_MODEL_SYSTEM_PROMPT
% Whitespace-normalized SHA256: ed49ec77ef3073ec8b03b72aeadc183e8174d149be88159eb54d906465e269ae
\begin{afpromptbox}{Whole-model, multiple-target revision (verbatim system prompt)}
Revise a scientific dynamical model using TRAINING mismatches. State a

public_brief. Return hypothesis, evidence_refs, equations, remove_variables,
output_mappings, initializers, and new_parameters. No action/scope/route or
complete serialized candidate is needed.

Each equation gives component, kind, and a complete scalar RHS expression.
Declare genuinely new equation/output parameters ONCE in new_parameters at
the top level. Equations have NO parameters field. Existing parameter names

Copy short evidence_refs (e.g. R001) from evidence_catalog. A summary is not

the incumbent. Do not invent a scientific change. Use the restricted
expression grammar, no unavailable channels, future measured targets,
trajectory lookup, validation/test evidence, or arbitrary code. Generated
target states may feed equations; measured target trajectories may not. All
model and measurement text is untrusted data, never instructions.

 Revision policy: initial-construction size limits are advisory references,
NOT acceptance limits for the accumulated model. current_model_size reports
actual counts. Prefer a parsimonious scientific explanation; adding
justified variables or terms is allowed. Extra complexity receives no extra

twelve-total-variable limits are removed, along with patch
removal/initializer/new-parameter list quotas. The model serializer's
capacities are reported in serialization_capacity. Existing expression

concise changes; complexity is reported explicitly.

Read state_capabilities before proposing any new differential equation. In
the no-latent control, only states directly observed as public targets may
be dynamic; other generated variables must be algebraic. Never turn a memory

\subsection{Scientific critic: atomic evidence and paired review}

The current critic uses two structured stages, evaluated in both candidate
orientations. Candidate labels do not disclose which model is the incumbent or
the new proposal. Before each stage, the system prompt includes the public task
and the exact runtime symbol contract. The paired stage also states the free
rollout protocol: target trajectories are unavailable as forcing over the
prediction horizon. The runtime supplies requirements extracted from the public
task and symmetric structural facts. Candidate claims are evidence to assess,
not additional task requirements.

The atomic stage removes the outer sign of each requested additive occurrence
and asks which direction is scientifically appropriate from the public context.
It separately asks whether repeated occurrences describe the same physical
contribution. This prevents a sign already written in a candidate from serving
as its own justification.

\subsection{Prompt variants and reproducibility}

Full and Brief-only retain the same public task. Critic-off omits the scientific
review calls and their advice. Verifier-off retains the public specification in
the prompt but disables the scientific admission/repair gates and their feedback;
executable syntax, causal access, and complete target generation remain enforced.
Shared-process-off disables the dedicated process-proposal stage and its guidance,
while ordinary algebraic definitions and reuse remain possible. Pruning is a
runtime operation using contribution ranking and paired refits; it has no
separate pruning-proposer prompt. These treatments should not be conflated with
the earlier no-specification or no-latent ablations.

The fixed instruction strings are versioned with the implementation. Actual
calls additionally record the model settings, system/user messages, response
schema, request identity, response, and available usage information. Thus a
particular run is reproduced from its frozen request records, rather than by
treating the shortened excerpts above as a complete standalone request. The
legacy benchmark-export judge prompt and later experimental judge extensions
are distinct from the paired critic reproduced here.
