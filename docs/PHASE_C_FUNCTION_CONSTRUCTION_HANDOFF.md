# Frozen function construction and scoped fitting handoff

Implemented 20 October 2026. This milestone continues the eight accepted
initializer declarations from `scope-aware-2`. It constructs executable formulas
and exports the existing scoped fitting problem. It does not choose which
initializer family to fit or launch optimization.

## Frozen inputs

The source inspection has ten episodes over two saved topologies and proposal
seeds 0–4. Eight are accepted: three dependent initial maps and five
trajectory-specific roots. The other two requested wider topology changes and
remain excluded, with their identities and outcomes retained in the roster.
Acceptance means no currently demonstrated deterministic conflict; the remaining
compatibility evidence is deferred, not resolved by a fitted model.

The source loader verifies the original archive, nested historical plans, full
drafts, projected inputs, accepted replies, call seeds and costs. It recovers the
authentic public brief and complete mechanism/external-exchange declarations.
It assembles the signed shared-process uses through the existing compiler; it
does not treat the ordinary-contribution list as the whole equation.

All eight accepted identities are kept, including identical dependency graphs
from different proposal seeds. No numerical score or family selection occurs.

## Construction

The existing staged function runner proposes a batch of functions for each
generated equation. Valid batch terms are retained; failed terms receive
targeted atomic repair. Shared-process definitions are constructed once and
their signed uses are assembled by the runtime. The selected sources, outer
signs, variable declarations and initializer dependencies/scopes remain fixed.
Formula replies cannot repair topology by silently adding a source or state.

The restricted expression grammar and explicit parameter-role schema remain
unchanged. Runtime namespacing and certified whole-term gain-domain corrections
use the existing policies; no fitted numbers are requested from the proposer.
Parameters remain unfitted when the campaign ends. Initializer formulas are
constructed after the dynamics: maps use their assigned initial-value aliases;
an independent root needs only a qualitative parameter role.

Each proposal has two attempts per requested slot, at most 96 physical requests
and 2,097,152 charged tokens across dynamics and initialization. The output
allowance is 8,192 tokens per request. On the current models the first-pass
minimum is 14 or 16 requests, including initialization. The fixed cap is a
ceiling, not a target. Every attempt is cached, including provider failures and
unknown usage. Resume retains those charges and the original identities.

`PROMPTS.html` contains exact first requests generated by the real runner and
clearly labeled templates for later stages. Later repair messages depend on
actual replies; all actual requests and responses are retained in `results`.
`REPORT.html` displays assembled equations, initialization rules and readiness
for every proposal. Failed constructions remain visible.

## Fitting boundary

A complete construction exports `prefix-fit-problem-1`, containing the
unlowered candidate, public context, executable initialization graph and
dynamics starts. Its separate receipt includes initializer aliases, shared
parameters, trajectory roots, dependent maps and retained evidence. The
top-level legacy candidate field remains null: this packet cannot accidentally
dispatch a trajectory root to the historical shared-parameter fitter.

The handoff distinguishes:

1. Restricted formula/dependency validation and exact reconstruction.
2. Static compilation by the existing scoped numerical adapter.
3. Forecast information access and unresolved prefix policy.

Static compilation performs no integration or optimization. Readiness does not
establish successful fitting, identifiable parameters, scientific correctness,
mechanism compliance or predictive accuracy. Prefix duration and the decision
of which proposals to fit remain future experiment settings.

Two concrete boundary details are preserved:

- In the first saved topology, generated differential `Uii` is internally
  aliased as a latent state, while its reviewed contract fixes its initial value
  to recorded `Uii(0)`. A runtime-owned zero-parameter identity map preserves
  that boundary. It adds no fitted coordinate, parameter, trajectory
  supervision or provider choice, and does not alter dynamics.
- The second topology consumes measured `EGP` and `Uii` histories. The current
  prefix forecaster permits declared future external inputs and fixed
  covariates, but does not support future measured auxiliary forcing.
  The export reports this limitation. It neither promotes these channels to
  inputs nor changes the model to work around it.

The portable fitting packet contains formulas, provenance and the retained
public training observations used for compatibility evidence. It is not a
complete training/validation/test fitting bundle. The subsequent fitting
experiment must explicitly bind its training inputs and frozen prefix policy.
No validation/test arrays or scores enter this construction campaign.

## ACES operation

`scripts/hpc/start_construction_functions_aces.sh` provides `run`, `status` and
`inspect`. It prepares a fresh `phase-c-functions-v1` root, then submits one
H100 job with 8 CPUs, 64 GB RAM and a two-hour allocation. The worker allowance
is 5,400 seconds, leaving time for startup and shutdown. Compiler caches use
node-local temporary storage to avoid the scratch inode problem.

The pinned model is `openai/gpt-oss-20b`, revision
`6cee5e81ee83917806bbde320786a8fb61efebee`, served locally through the existing
vLLM 0.27.1 image. CUDA, Harmony, image and serving identities are checked before
generation. Submission records prevent duplicate or uncertain resubmission.
There is no dependent fitting job and no automatic follow-up.

Run from the delivered pinned bundle:

```bash
bash run_functions.sh run
bash run_functions.sh status
bash run_functions.sh inspect
```

The final command writes `inspection.tar.gz` in the output root. A new
allocation may resume a draining campaign with a new explicit submission wave;
it does not reset call budgets or rerun completed proposals.

### A submitted job with a missing acknowledgement

A socket timeout from `sbatch` can occur after Slurm accepted the job. An empty
reply is therefore uncertain even when the wrapper reports exit code zero.
Inspect the queue before taking further action; do not remove the saved intent
or use a new wave to bypass it.

The standalone standard-library recovery command records an existing job after
checking its owner, submission time and complete submission command against the
saved intent. It also checks the original plan, execution and source identities.
It makes no submission or cancellation and does not alter campaign inputs,
scientific settings, results or budgets. Keep it outside the pinned bundle:

```bash
python3 recover_construction_functions_submission.py \
  --root /scratch/group/p.nairr260351.000/u.yx126462/phase-c-functions-v1 \
  --wave functions-1 --job-id 2236653
```

The original intent/reply are retained alongside an adoption audit, recovered
job-ID file and normal submission manifest. Repeating this recovery is safe;
conflicting metadata or insufficient scheduler evidence stops it. Recording a
failed job does not retry it. The worker itself needs the frozen plan and
execution files, so a missing submission manifest does not prevent it running.
