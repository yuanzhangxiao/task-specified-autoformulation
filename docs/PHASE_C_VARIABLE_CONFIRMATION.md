# Phase C: consistent contracts and explicit variable bindings

This implements the next bounded construction milestone after the first
32-construction audit. It does not modify benchmark prompts, data, old plans,
or fitting. The confirmation stops after variable definition.

## What the contract means

The legacy target contract was generated by our benchmark tooling for the
runtime's target-generation validator. It was not an LLM-generated judgment.
`phase_b_target_specs._public_target_representation` classified descriptions
containing `mass` as dynamic states and `rate` as instantaneous processes.
Those words identify physical quantities, not necessarily mathematical roles.
The Phase C scientific brief intentionally omitted this inference, but its final
target gate still inherited it. The adapter also bypassed the Phase B wrapper
that exposes the final contract before construction and repairs executable
drafts that fail public checks.

`phase-c-public-contract-consistency-1` corrects the exact reviewed legacy
descriptions for Dalla `Gp` and `U`. Their target roles become unspecified;
each still needs an explicit generated output. In particular, `Uii` composition,
causality, driver paths and dynamic-memory requirements remain. The correction
is an explicit adapter policy with before/after records and a source-contract
hash, not a new heuristic interpreting scientific prose. Other role declarations
are preserved. An explicit instantaneous-process requirement remains enforced.
Historical Phase B contracts and results are unchanged.

The new Phase C adapter reuses `review_multi_construction`: show the final
target contract from the first request, retain an executable failing draft,
and allow the existing maximum of three public-contract repair attempts within
the construction budget. Incomplete, nonexecutable constructions cannot use
this whole-model repair path. It is not a numerical revision round and receives
neither validation results nor independent mechanism assessments. Original route
attempts and public-contract repair attempts are saved separately.

## Who chooses the memory

Previously, `_record_memory_candidates` assigned the first eligible differential
variable returned for a memory agenda item. This happened during variable
definition, including its local retries, before process/topology construction.
The variable reply had no explicit assignment field. Reusing an existing state
with `variables=[]` therefore could not satisfy the runtime's memory gap.

The opt-in `explicit-variable-memory-bindings-1` response adds:

```json
{
  "variables": [],
  "mechanism_bindings": [
    {"requirement_id": "upstream_memory", "memory_states": ["h_up"]}
  ]
}
```

The proposer may bind existing or newly declared states and explicitly replace
an earlier binding in a subsequent variable reply. Omitted bindings are retained.
The runtime checks known requirement IDs, unique names, differential definitions,
and separation from that requirement's drivers/targets. It does not choose from
variable order or interpret `scientific_role`. Invalid binding transactions keep
the previous assignment; independently valid variable declarations survive and
are shown on retry. Public target roles are checked before committing variables
using the same role projection as the final contract.

This permits assignment repair, not unrestricted changes to accepted variable
definitions. Once inventory construction finishes, later topology still has to
establish the claimed paths. A mechanically valid binding is a scientific
hypothesis, not evidence that the pathway is correct.

## Context during repair

The original runner already resent the full scientific brief, inventory and
current equation sketch on each local retry. It did not retain a growing chat
transcript. The new Phase C path additionally supplies the complete committed
process declarations (all consumers, signs, conversions and scientific meanings)
and the selected variable's scientific role. The latest rejected reply and its
validation error are added to this same context. Automatic process insertion
and exact-repeat handling remain unchanged. A conflicting consumer/sign is not
silently reinterpreted; it needs a scientific revision.

`ConstructionClient` reuses the existing cached serving-tokenizer preflight.
With the pinned 32,768-token window and 8,192-token output allowance, its input
ceiling is 24,000 tokens, retaining at least 512 tokens of margin. Oversize or
unverifiable prompts produce a recorded preflight failure without generation;
scientific context is never silently truncated. Tokenization is recorded
separately from LLM generation cost. This establishes delivery consistency, not
that a 20B proposer will follow every constraint.

## Confirmation protocol and inspection

`phase_c_variables.py prepare` reads the previous sealed pilot plan and copies
only the public brief, context, corrected target contract and training summaries.
It retains the original eight-case roster, two seeds and Full/Brief-only variants:
32 variable constructions, including both basin cases. Raw training/validation
trajectories, fitted outcomes, independent predicates and old provider replies
are absent from the new plan. Brief-only receives no training summaries.
Settings and per-construction budgets are inherited; the plan and source identity
are freshly sealed. This is a new confirmation, not replay or promotion of an
old model. No topology/function/fitting/critic/pruning/test jobs are submitted.

The report distinguishes first replies, repairs and pending work. Progress
records also preserve skipped agenda items. `VARIABLES.html` links each
inventory/binding to `TRACE.html` with
exact requests, schemas, raw replies and acceptance events. `summary.json`
preserves per-task inventories, bindings, decisions and call costs. We must
manually assess whether the chosen variables and bindings meet the specification;
these counts are not mechanism compliance scores. After that review, the next
milestone can isolate topology/functions with reviewed inventories and eventually
connect to Orion's fitting study.
