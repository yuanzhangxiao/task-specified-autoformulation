# Initialization repair prompt audit

This audit accompanies the opt-in `focused-initialization-feedback-1`
presentation. Historical prompt policies, public benchmark text, model schemas,
and scientific acceptance rules remain unchanged. The initial-time diagnostic
correction is a separate change: shorter wording does not repair that check.

The audited input is the initialization-v2 inspection with plan hash
`acadff4c65226af0d5b72c5c4e86761abd0c3abc95daaa884b3236484abca126`,
15 saved episodes and 87 generated responses. Local evidence is in
`output/initialization-v2-analysis-20261016/inspection`. Paths below identify
task/event records within its `results` directory; these artifacts are not
committed. A rule's occurrence beside a failure is evidence of the failure, not
proof that the rule improves proposer behavior.

## Terminology

* **`mechanism_realizations`** is the proposer's attribution of components to a
  named public requirement. It is not a list of satisfied requirements. The
  declaration, path and behavioral checks retain their own status.
* **Algebraic equations** is restored in the system dictionary. No new mathematical
  interpretation or variable type is introduced by removing “instantaneous.”
* **`uses.target`** names a generated variable whose equation receives a process
  contribution. Declared public output targets are included. An observation or
  input that remains supplied-only can be an argument but is not generated by a
  candidate equation.
* **Shared process** denotes the separately declared reusable algebraic quantity;
  **local process** denotes an ordinary term. The stored schema field remains
  `processes`; that spelling is not a third scientific category.

Other editing rules are retained in a shorter contract: exact variable names,
one joint function for `sources=[x,z]`, process definition/use ownership,
replacement and removal semantics, known conversions versus fitted coefficients,
and response fields. These describe what a legal reply means; they do not all
need an observed mistake to justify their presence. Full JSON schema and response
template remain authoritative and unchanged.

The definition-ownership instruction now becomes specific when the previous
reply was rejected for a duplicate process definition. For example, T1-hard seed
1 event 003 proposed both a `processes` record for `D_to_Gp` and an `equations`
entry with that same name. Feedback names the conflicting entry and directs the
proposer to edit `depends_on`/`uses` in `processes`, omitting the extra equation
entry. It does not tell the proposer to delete the retained scientific process.

## Repeated context and reading priority

Each request currently has one system message and one user message; earlier
requests are not automatically part of the conversation. Removing the public
requirements because they appeared in a previous request would remove information
available to the proposer. Conversely, repeating a complete prior reply inside
feedback is not needed to remind it of unchanged public science.

The new presentation puts the short stage instruction, current repair work,
specific issues, previous-edit receipt and accepted model first. Initialization,
qualified compatibility questions, checklists and edit/schema information follow.
The full immutable public brief and training highlights remain at the end of the
same request. No observation, uncertainty bound, witness or public requirement is
removed or summarized away by this projection. Insertion-order serialization is
required; sorting JSON keys would erase this reading priority. Reordering by
itself is not a token saving and does not prove better attention.

Exact repeated compatibility fields are also displayed once in
`compatibility_details`, with explicit references from the affected questions.
Each target, question identifier, status and observed witness remains inline.
Only identical complete fields are shared; different assumptions, argument order
or observed differences remain distinct. Nested explanatory rules may be shared
without merging the questions. The projection is used only when it shortens the
serialized request, and an exact expansion test reconstructs the original fields.

The separate core mechanism mapping rule is shortened too. Optional-history,
assumption-challenge, external-handle, deletion and sign repair instructions are
attached only to applicable current findings. Existing exact issue-specific
feedback and factual receipts are preserved. There is no new benchmark-specific
repair rule.

## The 33 repeated declarations

T2-easy seed 2 event 005 was rejected for duplicate process keys. Its saved reply
contains **33 identical `basal_insulin_production` process records**. These were
present in the proposer output; the runtime did not manufacture 33 scientific
processes or accept them. The logs establish repeated generation, not its cause.
Calling it a model-capability limit, a scientific intention, or a response to one
particular prompt sentence would go beyond the evidence.

The runtime then echoed that whole rejected reply into its next feedback packet.
That enlarged an already long request. Under the new presentation, exact
consecutive records in `repeated_repair_feedback`'s `previous_reply` are displayed
once with a count and preserved order. An explicit marker identifies encoded
lists; `expand_repeated_reply` reconstructs the original arrays exactly. Other
fields, distinct records, current model records and scientific witnesses are not
compressed this way. Equal arguments alone never cause merging. No display
compression becomes an accepted model edit.

Duplicate-name feedback also now asks for one complete process record per name,
retaining all intended uses. It states explicitly that the repeated copies were
not committed. This is a format correction, not an instruction to collapse
distinct scientific processes.

## Verification and limits

Unit tests cover exact expansion of 33 repeated declarations, nonconsecutive
repetitions, distinct parameters and scalar types, malformed count rejection,
unchanged schema/evidence/current model, conditional guidance, initialization-only
requests and ordering. Budget prose now describes measured serving input tokens
plus output allowance and safety margin; it no longer describes UTF-8 bytes as
the reservation basis.

The effect on model quality requires the separately frozen saved-case retest.
The projection does not prove that shorter prompts improve scientific reasoning,
that three cases characterize the full suite, or that ACES and Jetstream serving
are numerically equivalent. The full benchmark run remains deferred.
